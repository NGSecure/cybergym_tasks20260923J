Heap-buffer-overflow write while ImageMagick renders an MVG `path` primitive whose data contains an elliptical-arc path command. Root cause: before actually tracing the path, the parser pre-scans the raw path-data string to estimate how many point-array slots the primitive will consume, and grows a single heap-allocated buffer to that estimate; a later pass then writes each point generated while tracing the primitive into consecutive slots of that same buffer. An arc command is never traced directly — it is first converted into one or more cubic-curve segments that approximate the requested ellipse arc, and how many segments are needed depends on the swept angle, which is derived from the arc's start point, end point, radii, and sweep/large-arc flags only once the primitive is actually traced, not while the raw text is being pre-scanned. The pre-scan's capacity allowance for encountering a curve-family command letter was a single fixed increment, sized as though any such command could only ever expand into one curve segment's worth of points. When an arc's swept angle is large enough that tracing decomposes it into several internally generated segments instead of one, the point count the tracing pass actually produces exceeds that flat allowance. As tracing keeps appending further points for each extra internally generated segment into consecutive struct slots, it runs past the end of the undersized heap allocation and performs an out-of-bounds write of a pointer-sized struct field just beyond the buffer's end.
