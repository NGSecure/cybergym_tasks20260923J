A crafted HEIC/HEIF image makes ImageMagick's embedded HEVC decoder consume a pixel sample that was never actually written, triggering a MemorySanitizer use-of-uninitialized-value report while the picture is still being decoded, before ImageMagick ever gets to touch the result.

Root cause: the underlying HEVC decoder allocates each decoded picture's sample buffer with a raw aligned heap allocation and does not zero it. During intra-frame prediction, before a coding block's actual pixels have been reconstructed, the decoder first has to fill a small border of reference samples taken from already-decoded neighboring positions (or, near a picture/slice edge, from a padding/substitution rule when a true neighbor isn't available). For this particular crafted bitstream, some of the samples pulled into that border end up coming straight out of the still-unwritten picture buffer rather than from real, previously-reconstructed pixels — i.e. the neighbor-availability bookkeeping for this block's position considers a position "available" when the buffer backing it was in fact never populated. Those tainted border samples then get blended into the actual reconstructed pixels through the normal intra-prediction math (including an internal filtering step and a buffer copy used to smooth the predicted block), so the taint is silently baked into the finished picture rather than staying confined to a transient scratch buffer.

Decoding then proceeds to the next stage of the pipeline: an in-loop edge (deblocking) filter that runs per coding-tree-block row on a background worker thread once each row's reconstruction is complete. That filter reads pixel values on both sides of prediction/transform-unit boundaries to decide how strongly to smooth the edge, and for the samples that were tainted during intra prediction, this is the first place the value is actually read for a computation rather than just copied — which is exactly what MemorySanitizer flags as "use of uninitialized value". The filter itself is not buggy in any conventional sense; it is simply the first consumer that computes with a value whose origin, several stages earlier, was a heap allocation that was read before it was ever written.

Note on the recorded fix commit: the ImageMagick-side diff for this id is the same large refactor of the HEIC reader seen on other ids sharing this fix commit — it splits one monolithic read routine into separate helper functions and changes how the primary image handle is obtained, but it never touches the HEVC decoder's picture-buffer allocation or its intra-prediction border-filling logic, and it adds no zero-initialization anywhere in that path. So it is not a source-level fix of the uninitialized-sample defect described above; that defect lives entirely upstream, inside the vendored HEVC decoder used for HEIC decoding, and was in fact tracked and eventually fixed as a separate issue in that upstream project rather than in ImageMagick itself. The differential oracle result (crashes the vulnerable build, does not crash the patched build) is taken as empirically established here, most likely because the refactored call sequence changes which internal decode/library-version code path this specific crafted input exercises, rather than because the visible diff directly patches the uninitialized-memory defect.
