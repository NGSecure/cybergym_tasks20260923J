A crafted HEIC/HEIF image makes ImageMagick's HEIF decode-then-encode round trip consume a pixel sample value that was never actually written, triggering a MemorySanitizer use-of-uninitialized-value report during output quantization.

Root cause: while decoding the embedded HEVC bitstream, the underlying HEVC decoder allocates a picture buffer and then applies the in-loop SAO (sample adaptive offset) filter, which copies filtered sample lines from the decoded picture on a worker thread. For this particular input, some of the samples that get copied out of that buffer were never populated by the preceding reconstruction/prediction stage (most likely an edge/alignment region of the frame that the general decode path does not fully populate for this frame's dimensions), so the copy propagates raw, uninitialized bytes rather than real pixel data. Those bytes are then bulk-copied again when the decoded picture is converted into the HEIF library's own image representation, and again when that image is rotated/transformed per the file's orientation metadata — none of these copies is a bug in itself, they just faithfully move whatever bytes are present, uninitialized or not.

ImageMagick's HEIF reader takes the Y/Cb/Cr sample planes from the decoded HEIF image handle as-is and stores each sample straight into its internal pixel representation, with no validation that every sample position was actually initialized by the decoder. The tainted sample survives untouched through that read path and only becomes externally observable later, when the image is written back out to HEIC: the output encoder down-converts the internal (higher-precision) pixel channel value to an 8-bit sample, and it is this narrowing/quantizing read of the still-uninitialized channel value that MemorySanitizer flags — i.e. the crash site is purely a consumer of a taint that was actually introduced much earlier, deep in the HEVC decode/filter stage, not a bug in the code that reports the warning.

Note on the recorded fix commit: the ImageMagick-side diff for this id is a large refactor of the HEIC reader (splitting one monolithic read function into separate color-profile/EXIF/per-image helper functions, switching to look up the primary image by ID instead of by handle, and fixing a couple of unrelated resource-leak paths on error). It does not touch the sample-copy loop that pulls Y/Cb/Cr planes into ImageMagick's pixel buffer, and it adds no zeroing/initialization of the decoded picture buffer, so it is not a source-level fix of the uninitialized-sample defect itself — that defect lives upstream, in the vendored HEVC decoder's picture-buffer handling. The differential oracle result (crashes the vulnerable build, does not crash the patched build) is taken as empirically established here, likely because the refactored call sequence changes which internal decode/library-version path this specific crafted input exercises, rather than because the visible diff directly patches the uninitialized memory.
