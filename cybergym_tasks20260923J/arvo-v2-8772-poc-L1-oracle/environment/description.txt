The vulnerable code parses a compact, textual path-drawing mini-language (the kind used to describe vector shapes such as arcs and curves) token by token, converting each token to a numeric value before using it to compute the geometry of a curved segment. One of the flag-like tokens that precedes an arc segment's endpoint coordinates was converted with a routine that simply returns zero whenever the text is not actually numeric, and the surrounding code never checked whether that conversion routine had consumed any characters at all, so a token that failed to parse as a number was silently accepted as though it meant "false" rather than being rejected as malformed input. Because that check was missing, the parser could advance past the arc-flag position without ever recognizing that nothing valid had been read there, letting the boundaries of subsequent tokens drift out of alignment with the crafted input that followed. The endpoint and control geometry computed from that misaligned state were then handed to the routine responsible for laying the segment's points into the shape's coordinate buffer, and the resulting write landed outside the memory actually sized for that shape, producing the out-of-bounds write the sanitizer caught. The fix closes the gap by switching that flag token to a floating-point conversion and explicitly checking that the conversion routine advanced past the token, raising a well-formed parse error for a non-numeric or empty flag instead of silently treating it as a valid falsy value and continuing to trace the arc from unvalidated state.
