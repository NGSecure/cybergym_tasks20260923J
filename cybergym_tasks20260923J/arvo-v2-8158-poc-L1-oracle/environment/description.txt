ImageMagick's HEIC reader hands the raw bytes off to its bundled libheif decoder, which crashes (MSan build) while reconstructing a "grid" HEIF image -- a HEIF image can be encoded as a mosaic of separately-coded tile images that the decoder is supposed to stitch back together into one full-size picture. Before doing that stitching, the decoder first parses a small grid-descriptor header for the item, which is expected to yield the tile grid's row count, column count, and the overall output width and height. The routine that owns this reconstruction calls the grid-descriptor parser but never inspects what it returns, and then goes straight on to read the row/column/width/height values out of the object the parser was supposed to have filled in, treating them as valid regardless of whether parsing actually completed.

The parser itself only fills those four fields in incrementally, in order, as it consumes descriptor bytes, and hands back an explicit failure indication the moment it decides the supplied descriptor buffer is too short to contain a legitimate header -- without touching whatever fields it hadn't gotten to yet. A descriptor buffer shorter than the minimum legitimate header size causes it to bail out before assigning any of the four fields at all; a descriptor that is long enough to carry the row/column byte pair but selects an extended (wider) width/height encoding via one of its header flag bits, while still being too short to actually hold that wider encoding, causes it to bail out after only the row/column fields have been set, leaving the width/height fields untouched.

Because the caller ignores the failure indication in both cases, reconstruction proceeds as if a genuine grid header had been read. The row and column counts (uninitialized stack garbage in the first case) get multiplied together and compared against the number of tile-image references actually present for the item, feeding straight into a diagnostic message and a bounds check; the width and height (uninitialized in either case) get compared against a maximum-image-size limit and then used directly as the dimensions for allocating the reconstructed image's pixel planes and driving the nested loop that walks the tile grid and stitches each tile into its place in the output. All of this downstream arithmetic, allocation sizing, and loop bounding runs on top of whatever leftover values happened to be sitting on the stack, which is what the sanitizer flags as soon as one of those uninitialized fields is first read back out.

The fix is small and mechanical: the reconstruction routine now captures the descriptor parser's return value and immediately propagates a failure back to its own caller instead of silently continuing, exactly the same way it already handles its other error conditions (missing reference metadata, tile-count mismatches, oversized dimensions) a few lines further down in the same function.
