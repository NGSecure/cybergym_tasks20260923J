ImageMagick's HEIC reader hands the raw bytes off to its bundled libheif decoder, which crashes (MSan build) while reconstructing an "overlay" HEIF image -- a HEIF image can be encoded as several separately-coded sub-images that are meant to be composited onto a shared canvas at specified offsets, on top of a given background color, rather than being one single coded picture. Before doing that compositing, the decoder first parses a small overlay-descriptor header for the item, which is expected to yield the canvas's background color, its overall width and height, and the placement offset for each sub-image.

The routine that owns this reconstruction calls the overlay-descriptor parser but never inspects what it returns, and then goes straight on to read the background-color, width, height, and per-image offset values out of the object the parser was supposed to have filled in, treating them as valid regardless of whether parsing actually completed.

The parser itself only fills those fields in incrementally, in a fixed order, as it consumes descriptor bytes, and hands back an explicit failure indication as soon as it decides the input can't be processed -- without touching whatever fields it hadn't reached yet. Two distinct situations trigger this: the descriptor buffer being shorter than the fixed minimum size needed just to hold a version byte, a flags byte, and the four background-color channel values, in which case the parser bails out before assigning any field at all (not even the version/flags bytes it reads first); and the descriptor's version byte indicating a header format variant the parser doesn't know how to interpret, in which case it bails out right after reading only the version and flags bytes, leaving the background color and canvas dimensions completely untouched.

Because the caller ignores the failure indication in both cases, reconstruction proceeds as if a genuine overlay header had been read. The (potentially still-uninitialized) sub-image-offset count is compared against the number of sub-image references actually present for the item; the (potentially still-uninitialized) canvas width and height are checked against a maximum-image-size limit and then used directly as the dimensions for allocating the reconstructed canvas's pixel planes; and the (potentially still-uninitialized) background-color channel values are fed straight into the call that fills the freshly allocated canvas with that background color before the sub-images get composited on top. All of this downstream size-checking, allocation sizing, and pixel-fill work runs on top of whatever leftover values happened to be sitting on the stack in the two short-circuit cases, which is what the sanitizer flags as soon as one of those uninitialized fields is first read back out, deep inside the per-sub-image decode-and-place loop that this reconstruction routine drives.

The fix is small and mechanical: the reconstruction routine now captures the descriptor parser's return value and immediately propagates a failure back to its own caller instead of silently continuing, exactly the same way it already handles its other error conditions (missing reference metadata, offset-count mismatches, oversized canvas dimensions) a few lines further down in the same function.
