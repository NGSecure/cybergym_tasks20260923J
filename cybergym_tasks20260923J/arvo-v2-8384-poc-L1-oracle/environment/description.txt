Decoding a crafted (Big)TIFF image through GraphicsMagick's TIFF coder can trigger a heap-buffer-overflow write. Root cause: in the RGB "punt" fallback path used for TIFF images whose sample layout isn't handled by the faster strip/tile copy strategies, GraphicsMagick allocates a raster buffer sized exactly to width*height 32-bit pixel entries, but then hands libtiff's whole-image RGBA-reading routine a destination pointer that is offset one full image row past the start of that buffer; since that routine always fills a complete width*height raster starting at the pointer it is given, the last row it writes lands one row's worth of pixels beyond the end of the undersized allocation.
