ImageMagick's TIFF decoder (ASan build, exercised through a raw-TIFF encoder fuzz target): while libtiff parses a directory entry for an undocumented, vendor-specific numeric metadata tag, it allocates the internal storage that will hold that tag's value with a size driven strictly by the tag's actual on-disk data type and count as declared in the file, not by whatever width a downstream consumer later assumes. A later metadata-import step, which copies a handful of auxiliary TIFF tags (artist, timestamp, a couple of vendor-specific numeric fields, and so on) into the image's reportable properties, fetches the pointer libtiff handed back for that private numeric tag and immediately reads a full native-width (8-byte) integer out of it, without first checking that the buffer libtiff actually allocated for that tag is wide enough to hold one. Because a crafted input can declare the private tag using a narrower on-disk type than an 8-byte value implies, libtiff ends up allocating only a couple of bytes for it; the unconditional wide read then walks past the end of that small heap allocation, producing an out-of-bounds heap read.
